บท 4 — HTTP/API แบบ Async และ workflow หลายขั้น
========================================================================

[HTTP-01] HTTP client ที่เหมาะกับ async
HTTPX AsyncClient ใช้ await client.get/post และ async with ปิด connection
ใช้ client ร่วมกันภายใน workflow เพื่อ reuse connection pool
GET มักอ่านข้อมูล; POST ส่งข้อมูลให้บริการตาม API contract
params=... ส่ง query; json=... ส่ง JSON body
raise_for_status() ตรวจ HTTP error; response.json() แปลง JSON โดยไม่ต้อง await
HTTP 200 ไม่ได้แปลว่าธุรกิจสำเร็จเสมอ ต้องอ่าน status ใน body ด้วย

[HTTP-02] ลำดับภายใน workflow
งานลูกค้า/robot คนละตัวรันร่วมกันได้ แต่ขั้นตอนภายในตัวเดียวต้องเรียงตาม dependency
Week6/robots.py: reset_factory ก่อน gather(*robot_tasks)
run_robot_task แต่ละตัว await grab_part ตามลำดับชิ้นส่วน
Week4/light/light_utils.py: ตรวจ light id และค่าที่อนุญาตก่อนส่ง request

ตัวอย่างต่อไปนี้เป็น template สำหรับบริการของตนเอง ไม่ใช่ endpoint ห้องเรียน
ต้องมี HTTPX และ server ที่ตอบ JSON; แก้ URL ให้ตรงโจทย์

[CODE http_template]
import asyncio  # รัน coroutine
import httpx  # ต้องมีไลบรารี HTTPX
async def fetch(client, url):  # ใช้ client ร่วมกัน
    response = await client.get(url)  # ส่ง GET แล้วรอแบบ async
    response.raise_for_status()  # ตรวจสถานะ HTTP
    return response.json()  # JSON parsing เป็นคำสั่ง synchronous
async def main():  # จัดการอายุ client
    async with httpx.AsyncClient(timeout=5.0) as client:
        data = await fetch(client, "http://127.0.0.1:8000/items/1")
        print(data)  # ผลขึ้นกับ server ที่ใช้งาน
asyncio.run(main())  # รันในสคริปต์
[END CODE]

[HTTP-03] แก้ปัญหาจากอาการ
Connection refused -> ตรวจว่าบริการรันและ port ตรง
404 -> ตรวจ path และ method
422 -> ตรวจชื่อ field, type และรูปแบบ body ตาม FastAPI schema
timeout -> แยก network/บริการช้า; ไม่ retry POST โดยไม่คิดการทำซ้ำ
ผลลัพธ์ผิดลำดับ -> gather คืนตาม input; อย่าเรียงจากเวลาจบโดยเดา

อ้างอิง repo: Week3/stock_price_httpx.py, Week4/food_utils.py,
Week5/fastapi_async_external_api_lab.py และ Week6/robots.py

3. คำศัพท์ที่ต้องรู้
--------------------

- คำ: Client
  ความหมายง่าย ๆ: โปรแกรมที่ส่งคำขอ
  ใน Lab นี้: Python ของใบ

- คำ: Server
  ความหมายง่าย ๆ: โปรแกรมที่รับคำขอและส่งผลกลับ
  ใน Lab นี้: Server 172.16.2.117:8088

- คำ: REST API
  ความหมายง่าย ๆ: ช่องทาง HTTP ที่ Client ใช้สั่ง Server
  ใน Lab นี้: GET, POST, DELETE

- คำ: Endpoint
  ความหมายง่าย ๆ: Method และ URL ที่ใช้เรียกงานหนึ่งอย่าง
  ใน Lab นี้: POST /api/.../lights/light_1

- คำ: Request
  ความหมายง่าย ๆ: ข้อมูลที่ Client ส่งไป
  ใน Lab นี้: JSON {"status": "ON"}

- คำ: Response
  ความหมายง่าย ๆ: ข้อมูลที่ Server ตอบกลับ
  ใน Lab นี้: JSON สถานะปัจจุบัน

- คำ: JSON
  ความหมายง่าย ๆ: รูปแบบข้อมูล key-value
  ใน Lab นี้: {"light_id": "light_1"}

- คำ: Latency
  ความหมายง่าย ๆ: เวลาหน่วงก่อน Server ตอบ
  ใน Lab นี้: light_3 ใช้ 2.0 วินาที

- คำ: Coroutine
  ความหมายง่าย ๆ: งานที่ประกาศด้วย async def
  ใน Lab นี้: set_light()

- คำ: Task
  ความหมายง่าย ๆ: Coroutine ที่ Event Loop รับไปจัดการ
  ใน Lab นี้: งานจาก asyncio.gather()

- คำ: Event Loop
  ความหมายง่าย ๆ: ตัวสลับและจัดคิวงาน async
  ใน Lab นี้: เริ่มด้วย asyncio.run()

- คำ: Sequential
  ความหมายง่าย ๆ: ทำทีละงานและรอทีละงาน
  ใน Lab นี้: light_01.py

- คำ: Concurrent
  ความหมายง่าย ๆ: หลายงานคืบหน้าในช่วงเวลาเดียวกัน
  ใน Lab นี้: light_02.py

- คำ: WebSocket
  ความหมายง่าย ๆ: Connection ที่ Server push ข้อมูลมาได้
  ใน Lab นี้: Dashboard รับสถานะใหม่ทันที

- คำ: Timeout
  ความหมายง่าย ๆ: เวลารอสูงสุด
  ใน Lab นี้: HTTPX timeout

8. Error จาก API ที่ต้องรู้
---------------------------

- HTTP Status: 200
  ความหมาย: สำเร็จ
  ตัวอย่างสาเหตุ: เปิดไฟได้

- HTTP Status: 400
  ความหมาย: ค่าที่ส่งไม่ถูกต้อง
  ตัวอย่างสาเหตุ: ส่ง OPEN แทน ON

- HTTP Status: 404
  ความหมาย: ไม่พบ resource
  ตัวอย่างสาเหตุ: ใช้ light_5

- HTTP Status: 422
  ความหมาย: JSON ไม่ตรงรูปแบบ
  ตัวอย่างสาเหตุ: ไม่ส่ง field status

9. ทำไมใช้ httpx.AsyncClient
----------------------------

httpx เป็น library สำหรับส่ง HTTP request จาก Python

แบบ async ใช้:

[โค้ด / แผนภาพ : python]
async with httpx.AsyncClient(...) as client:
    response = await client.get(...)
[จบโค้ด / แผนภาพ]

ข้อดี:

- รองรับ await
- ระหว่างรอ network Event Loop ไปจัดการงานอื่นได้
- ใช้กับ asyncio.gather() ได้
- เหมาะกับการส่งหลาย request พร้อมกัน

async with ช่วยเปิดและปิด connection อย่างถูกต้อง

-----------------------

        v

        |
        v
POST เปิด light_1 -> รอ 0.5s
        |
        v
POST เปิด light_2 -> รอ 1.2s
        |
        v
POST เปิด light_3 -> รอ 2.0s
        |
        v
POST เปิด light_4 -> รอ 0.8s
        |
        v
GET สถานะสุดท้าย
        |
        v
Reset กลับเป็น OFF
[จบโค้ด / แผนภาพ]

หัวใจของโค้ด:

[โค้ด / แผนภาพ : python]
for light_id in LIGHT_IDS:
    result = await set_light(client, light_id, "ON")
[จบโค้ด / แผนภาพ]

จุดสำคัญคือ loop จะรอแต่ละ request ให้เสร็จก่อนเริ่มตัวถัดไป

14. light_02.py — Concurrent ด้วย asyncio.gather()
--------------------------------------------------

ไฟล์นี้สอนการเปิดไฟทั้ง 4 ดวงแบบ Concurrent

Flow:

[โค้ด / แผนภาพ : text]
Reset ไฟทั้งหมดเป็น OFF
        |
        v
GET สถานะเริ่มต้น
        |
        v
สร้างคำสั่ง POST ทั้ง 4 ดวง
        |
        v
asyncio.gather()
        |
        ├── light_1 รอ 0.5s
        ├── light_2 รอ 1.2s
        ├── light_3 รอ 2.0s
        └── light_4 รอ 0.8s
        |
        v
รอจนทุกดวงเสร็จ
        |
        v
GET สถานะสุดท้าย
        |
        v
Reset กลับเป็น OFF
[จบโค้ด / แผนภาพ]

หัวใจของโค้ด:

[โค้ด / แผนภาพ : python]
results = await asyncio.gather(
    *(set_light(client, light_id, "ON") for light_id in LIGHT_IDS)
)
[จบโค้ด / แผนภาพ]

* ทำอะไร
------------

ส่วนนี้สร้างงานหลายตัว:

[โค้ด / แผนภาพ : python]
set_light(client, "light_1", "ON")
set_light(client, "light_2", "ON")
set_light(client, "light_3", "ON")
set_light(client, "light_4", "ON")
[จบโค้ด / แผนภาพ]

เครื่องหมาย * แตก iterable ให้กลายเป็น argument หลายตัวของ gather()

เวลาที่คาด
------------

ทุก request เริ่มใกล้กัน เวลารวมจึงขึ้นกับไฟที่ช้าที่สุด:

[โค้ด / แผนภาพ : text]
max(0.5, 1.2, 2.0, 0.8) = 2.0 วินาที
[จบโค้ด / แผนภาพ]

ไม่ใช่ผลรวม 4.5 วินาที

ลำดับของ results
----------------

gather() คืนผลลัพธ์ตามลำดับ argument ที่ส่งเข้าไป:

[โค้ด / แผนภาพ : text]
results[0] -> light_1
results[1] -> light_2
results[2] -> light_3
results[3] -> light_4
[จบโค้ด / แผนภาพ]

แม้ลำดับเวลาที่ Server ทำเสร็จจะเป็น:

[โค้ด / แผนภาพ : text]
light_1 -> light_4 -> light_2 -> light_3
[จบโค้ด / แผนภาพ]

นี่เป็นคำถามที่มีโอกาสออกสอบค่ะ

Part D — Safety และ Error Handling
==================================

17. ทำไมต้องใช้ try/finally
---------------------------

ถ้าโปรแกรมเกิด error กลางทาง เราไม่อยากให้ไฟค้างเป็น ON

รูปแบบ:

[โค้ด / แผนภาพ : python]
try:
    # ทดลองเปิดไฟ
finally:
    # reset กลับ OFF เสมอ
[จบโค้ด / แผนภาพ]

finally จะถูกพยายามเรียกไม่ว่า:

- โปรแกรมสำเร็จ
- เกิด HTTP error
- เกิด exception ระหว่าง loop

ข้อควรรู้: ถ้า network ขาดในช่วง finally การ reset ก็อาจล้มเหลวได้ จึงต้องรายงาน error
ตามจริง ไม่ควรอ้างว่า reset สำเร็จโดยไม่ได้รับ response

----------------------------------------------------------------

18. ทำไมไม่ควรจับ Exception กว้าง ๆ ใน Helper
---------------------------------------------

แบบที่ไม่ดี:

[โค้ด / แผนภาพ : python]
try:
    ...
except Exception:
    return {}
[จบโค้ด / แผนภาพ]

ปัญหา:

- กลบสาเหตุจริง
- Caller แยกไม่ได้ว่า HTTP 404, timeout หรือ code bug
- Dictionary ว่างอาจถูกเข้าใจผิดว่า response สำเร็จ

แนวทางที่ชัดกว่า:

[โค้ด / แผนภาพ : python]
response.raise_for_status()
return response.json()
[จบโค้ด / แผนภาพ]

แล้วให้ระดับ CLI จับ httpx.HTTPError เพื่อแสดงข้อความแก่ผู้ใช้

----------------------------------------------------------------

19. ระวัง Cancel และ Timeout กับคำสั่ง POST
-------------------------------------------

ถ้า Client cancel การรอ HTTP request ไม่ได้แปลว่า Server จะ rollback

ตัวอย่าง:

[โค้ด / แผนภาพ : text]
Client ส่ง POST เปิด light_3
Server รับคำสั่งแล้ว
Client timeout ก่อน 2 วินาที
Server อาจทำงานต่อและเปิดไฟสำเร็จ
[จบโค้ด / แผนภาพ]

ดังนั้น:

[โค้ด / แผนภาพ : text]
Client timeout != ยืนยันว่า Server ไม่เปลี่ยนสถานะ
[จบโค้ด / แผนภาพ]

วิธีตรวจที่ถูก:

1. รับมือ timeout
2. รอสักระยะถ้าจำเป็น
3. GET สถานะจาก Server อีกครั้ง
4. ใช้สถานะจาก Server เป็นความจริงล่าสุด

ด้วยเหตุนี้ Lab หลักจึงเน้น Sequential กับ gather() และไม่ใช้ FIRST_COMPLETED แล้ว
cancel POST ที่เหลือค่ะ

38. สรุปสุดท้าย
---------------

จำ 5 ข้อนี้ให้ได้:

1. Python ของใบเป็น Client ที่ส่ง HTTP request ไปยัง Server
2. GET อ่านสถานะ, POST เปิด/ปิดไฟ, DELETE รีเซ็ต
3. light_01.py รอทีละดวง จึงใช้เวลาประมาณ 4.5 วินาที
4. light_02.py ใช้ asyncio.gather() จึงใช้เวลาประมาณ 2.0 วินาที
5. Dashboard รับ WebSocket broadcast และเปลี่ยน real-time

ประโยคสรุปสำหรับตอบอาจารย์:

งานนี้ใช้ httpx.AsyncClient ส่ง REST API requests ไปควบคุมไฟจำลอง 4 ดวง
โดยเปรียบเทียบการ await ทีละ request กับการรันพร้อมกันผ่าน asyncio.gather() แบบ
sequential ใช้เวลารวมของทุก delay ประมาณ 4.5 วินาที ส่วน concurrent
ใช้เวลาใกล้กับงานที่ช้าที่สุดประมาณ 2.0 วินาที และ Dashboard รับสถานะใหม่แบบ real-time
ผ่าน WebSocket ค่ะ

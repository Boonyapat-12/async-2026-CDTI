[API-01] เลือก def / async def
FastAPI เรียก path operation แบบ def ผ่าน thread pool
path operation แบบ async def ทำบน event loop และควรใช้ async I/O
helper def ที่เรียกตรงจาก async def ไม่ถูกย้ายเข้า thread pool ให้อัตโนมัติ
time.sleep ใน async def บล็อก loop; await asyncio.sleep ยอมให้งานอื่นเดิน
Week5/fastapi_async_basic_lab.py มี /sync-delay และ /async-delay ให้เปรียบเทียบ

template ต่อไปนี้บันทึกเป็น demo_api.py เมื่อมี FastAPI/Uvicorn
คำสั่ง: python -m uvicorn demo_api:app --port 8000
ทดสอบ: GET http://127.0.0.1:8000/delay -> {"ok": true}

[CODE fastapi_template]
import asyncio  # ใช้การรอแบบ async
from fastapi import FastAPI  # สร้าง API
app = FastAPI()  # instance ของ application
@app.get("/delay")  # ระบุ method และ path
async def delay():  # handler แบบ async
    await asyncio.sleep(0.01)  # คืนการควบคุมระหว่างรอ
    return {"ok": True}  # FastAPI แปลงเป็น JSON response
[END CODE]

[WS-01] WebSocket ต่างจาก HTTP request/response อย่างไร?
WebSocket เป็น connection ที่เปิดไว้เพื่อส่งข้อมูลสองทิศทางหลายข้อความ
เหมาะกับ live dashboard/chat; ไม่ต้องส่ง GET ใหม่เพื่อรับทุก update
server ต้อง accept connection ก่อนใช้งาน แล้ว receive/send ตาม protocol
ต้องจัดการ disconnect และนำ connection ออกจากรายการผู้รับ
ผู้รับช้าอาจทำให้ sequential broadcast ช้า ต้องออกแบบ buffering/backpressure

[CODE websocket_template]
from fastapi import FastAPI, WebSocket, WebSocketDisconnect  # WebSocket API
app = FastAPI()  # application
@app.websocket("/ws")  # route ของ WebSocket
async def echo(ws: WebSocket):  # connection แต่ละตัวมี handler
    await ws.accept()  # ยอมรับ connection
    try:
        while True:  # อ่านจน client disconnect
            text = await ws.receive_text()  # รอข้อความ
            await ws.send_text(text)  # ตอบกลับข้อความเดิม
    except WebSocketDisconnect:  # client ปิด connection
        pass  # ตัวอย่างไม่มีรายการ connection ให้ล้าง
[END CODE]

ผลที่คาดหวังเมื่อรัน server และใช้ WebSocket client: ส่ง hello แล้วรับ hello
template นี้ไม่มี authentication หรือ deployment configuration
repo: Week5/chat-hello/main.py, Week5/rocket/main.py,
Week10/web_dashboard.py: Redis listener รับ state แล้ว ConnectionManager broadcast

2. คำศัพท์พื้นฐาน
-----------------

- คำ: FastAPI
  ความหมายแบบง่าย: Framework สำหรับสร้างเว็บ API ด้วย Python
  ตัวอย่างในโค้ด: app = FastAPI(...)

- คำ: Uvicorn
  ความหมายแบบง่าย: ASGI server ที่นำ FastAPI app ไปรัน
  ตัวอย่างในโค้ด: uvicorn main:app ...

- คำ: Route / Endpoint
  ความหมายแบบง่าย: Method และ path ที่เปิดให้ client เรียก
  ตัวอย่างในโค้ด: GET /users, WS /ws/{client_id}

- คำ: HTTP GET
  ความหมายแบบง่าย: ขออ่านข้อมูล
  ตัวอย่างในโค้ด: @app.get("/")

- คำ: HTTP POST
  ความหมายแบบง่าย: ส่งข้อมูลไปให้ server ประมวลผล
  ตัวอย่างในโค้ด: @app.post("/register/student")

- คำ: Path parameter
  ความหมายแบบง่าย: ค่าที่ฝังอยู่ใน path
  ตัวอย่างในโค้ด: item_id ใน /items/{item_id}

- คำ: Query parameter
  ความหมายแบบง่าย: ค่าหลัง ? ใน URL
  ตัวอย่างในโค้ด: ?username=Alice&age=21

- คำ: Request body
  ความหมายแบบง่าย: ข้อมูลหลักที่ส่งมากับ request
  ตัวอย่างในโค้ด: JSON ของนักศึกษา

- คำ: JSON
  ความหมายแบบง่าย: ข้อมูลแบบ key-value
  ตัวอย่างในโค้ด: {"type":"CONTROL"}

- คำ: Pydantic model
  ความหมายแบบง่าย: สัญญารูปแบบและชนิดข้อมูล
  ตัวอย่างในโค้ด: SimpleStudent(BaseModel)

- คำ: Validation
  ความหมายแบบง่าย: ตรวจว่าข้อมูลตรง schema หรือไม่
  ตัวอย่างในโค้ด: gpa ต้องแปลงเป็น float ได้

- คำ: Sync / Blocking
  ความหมายแบบง่าย: งานครอบครอง thread ขณะรอ
  ตัวอย่างในโค้ด: time.sleep(3)

- คำ: Async / Non-blocking wait
  ความหมายแบบง่าย: ยอมคืน control ให้ event loop ระหว่างรอ
  ตัวอย่างในโค้ด: await asyncio.sleep(3)

- คำ: Coroutine
  ความหมายแบบง่าย: งานจาก function ที่ประกาศ async def
  ตัวอย่างในโค้ด: fetch_single_api()

- คำ: Event loop
  ความหมายแบบง่าย: ตัวสลับให้งาน async หลายงานคืบหน้า
  ตัวอย่างในโค้ด: ทำงานเมื่อ Uvicorn รัน app

- คำ: Concurrency
  ความหมายแบบง่าย: หลายงานคืบหน้าสลับกันระหว่างรอ
  ตัวอย่างในโค้ด: asyncio.gather(...)

- คำ: HTTPX
  ความหมายแบบง่าย: HTTP client ที่รองรับ async
  ตัวอย่างในโค้ด: httpx.AsyncClient()

- คำ: Timeout
  ความหมายแบบง่าย: เวลารอสูงสุด
  ตัวอย่างในโค้ด: timeout=3.0

- คำ: Fallback
  ความหมายแบบง่าย: ข้อมูลสำรองเมื่อบริการจริงล้มเหลว
  ตัวอย่างในโค้ด: MOCK_CAT_FACT

- คำ: Graceful degradation
  ความหมายแบบง่าย: บริการยังตอบได้แม้บางส่วนเสีย
  ตัวอย่างในโค้ด: เปลี่ยนไปคืน mock data

- คำ: WebSocket
  ความหมายแบบง่าย: connection สองทางที่เปิดค้างไว้
  ตัวอย่างในโค้ด: /ws/{student_id}

- คำ: Broadcast
  ความหมายแบบง่าย: ส่งข้อความเดียวให้ทุก connection
  ตัวอย่างในโค้ด: manager.broadcast(...)

- คำ: Canvas
  ความหมายแบบง่าย: พื้นที่วาดกราฟิกใน browser
  ตัวอย่างในโค้ด: <canvas width="800" height="600">

- คำ: SPAWN / UPDATE / DESPAWN
  ความหมายแบบง่าย: event เกิด/เปลี่ยน/หายของจรวด
  ตัวอย่างในโค้ด: JSON จาก Rocket server

4. Week5/fastapi_async_basic_lab.py
-----------------------------------

4.1 Endpoint ทั้งหมด
--------------------

- Method: GET
  Path: /sync-delay
  วิธีรอ: time.sleep(3)
  เวลาที่คาด: ~3 วินาที

- Method: GET
  Path: /async-delay
  วิธีรอ: await asyncio.sleep(3)
  เวลาที่คาด: ~3 วินาทีสำหรับ request นั้น

- Method: GET
  Path: /concurrent-tasks
  วิธีรอ: asyncio.gather() รอ 2, 3, 1 วินาทีพร้อมกัน
  เวลาที่คาด: ~3 วินาที


4.2 /sync-delay — synchronous blocking
--------------------------------------

[โค้ด / แผนภาพ : python]
@app.get("/sync-delay")
def sync_delay():
    time.sleep(3)
[จบโค้ด / แผนภาพ]

time.sleep(3) block thread ที่กำลังรัน function นั้นอยู่เต็ม 3 วินาที
โค้ดอธิบายไว้อย่างถูกต้องว่า FastAPI นำ endpoint แบบ def ไปทำใน thread pool
จึงไม่ควรสรุปง่ายเกินไปว่า “ทำให้ทั้ง server หยุดทั้งหมด” แต่ request นี้ยังครอบครอง
worker thread ระหว่างรอ

4.3 /async-delay — cooperative asynchronous wait
------------------------------------------------

[โค้ด / แผนภาพ : python]
@app.get("/async-delay")
async def async_delay():
    await asyncio.sleep(3)
[จบโค้ด / แผนภาพ]

Request นี้ยังใช้เวลาประมาณ 3 วินาทีเหมือนเดิม แต่ระหว่าง sleep coroutine คืน control
ให้ event loop เพื่อดูแลงานอื่นได้

[โค้ด / แผนภาพ : text]
เวลา request เดียว:
/sync-delay  ≈ 3 วินาที
/async-delay ≈ 3 วินาที

ความต่างสำคัญ:
time.sleep       -> block thread
await async sleep -> ยอมให้ event loop ไปทำงานอื่น
[จบโค้ด / แผนภาพ]

async def ไม่ได้ทำให้ทุกอย่างเร็วเอง ถ้าใส่ blocking code ลงใน async def
ก็ยังสร้างปัญหาได้

4.4 /concurrent-tasks — asyncio.gather()
----------------------------------------

Helper ภายใน endpoint จำลอง 3 API:

- งาน: API_Alpha
  เวลารอ: 2 วินาที
  ผลที่ return: Data from API_Alpha

- งาน: API_Beta
  เวลารอ: 3 วินาที
  ผลที่ return: Data from API_Beta

- งาน: API_Gamma
  เวลารอ: 1 วินาที
  ผลที่ return: Data from API_Gamma


[โค้ด / แผนภาพ : python]
results = await asyncio.gather(
    fetch_data_from_api("API_Alpha", 2),
    fetch_data_from_api("API_Beta", 3),
    fetch_data_from_api("API_Gamma", 1)
)
[จบโค้ด / แผนภาพ]

ถ้ารอทีละงานจะเป็น 2 + 3 + 1 = 6 วินาที แต่ gather() ทำให้ทั้งสามคืบหน้าพร้อมกัน
จึงรอประมาณงานช้าที่สุดคือ 3 วินาที

สิ่งที่มักออกสอบ:

- ลำดับ เสร็จ: Gamma, Alpha, Beta
- ลำดับใน results: Alpha, Beta, Gamma ตามลำดับ argument ของ gather()
- นี่คือ concurrency ของงานรอ I/O ไม่ควรเรียกว่าใช้ CPU คำนวณสามงานแบบ parallel
  โดยอัตโนมัติ

  URL ในโค้ด: https://official-joke-api.appspot.com/random_joke
  Mock data เมื่อเรียกไม่ได้: มุก dark mode / bugs


ผลจากบริการจริงเปลี่ยนได้ และบริการอาจ timeout, rate-limit, เปลี่ยนรูปแบบ หรือเข้าไม่ได้
โค้ดจึงมี fallback เพื่อให้ endpoint ของเรายังตอบได้

- Method: GET

5.3 รูปแบบ HTTPX ที่ต้องจำ
--------------------------

[โค้ด / แผนภาพ : python]
async with httpx.AsyncClient() as client:
    response = await client.get(url, timeout=3.0)
    response.raise_for_status()
    data = response.json()
[จบโค้ด / แผนภาพ]

- บรรทัด: AsyncClient()
  หน้าที่: client สำหรับ network I/O แบบ async

- บรรทัด: async with
  หน้าที่: ปิด client/connection resource เมื่อจบ block

- บรรทัด: await client.get(...)
  หน้าที่: ส่ง GET โดยไม่ block event loop ระหว่างรอ network

- บรรทัด: timeout=3.0
  หน้าที่: รอ request นั้นสูงสุด 3 วินาที

- บรรทัด: raise_for_status()
  หน้าที่: เปลี่ยน HTTP error status เป็น exception

- บรรทัด: response.json()
  หน้าที่: แปลง JSON response เป็น Python object

-----------------

[โค้ด / แผนภาพ : json]
{
  "status": "Success",
  "elapsed_seconds": 0.42,
  "source": "CatFact Ninja",
  "fallback_activated": false,
  "fetched_payload": {"fact": "...", "length": 123}
}
[จบโค้ด / แผนภาพ]

เมื่อเกิด httpx.HTTPError:

- server print network warning
- ใช้ MOCK_CAT_FACT
- fallback_activated เป็น true
- endpoint ยังคืน status: "Success" ตามโค้ด เพราะ success ในที่นี้หมายถึง endpoint

5.5 /sequential-fetch
---------------------

ลำดับการรอจริง:

[โค้ด / แผนภาพ : text]
Cat เสร็จ/ล้มเหลว
       |
       v
Bitcoin เสร็จ/ล้มเหลว
       |
       v
Joke เสร็จ/ล้มเหลว
       |
       v
return ผลรวม
[จบโค้ด / แผนภาพ]

แม้ใช้ await และไม่ block event loop แต่ภายใน request นี้ยัง รอแบบเรียงลำดับ เพราะ
request ถัดไปเริ่มหลัง request ก่อนหน้าจบ

กรณีเลวร้ายที่ทั้งสามรอจน timeout 3 วินาที เวลารวมอาจเข้าใกล้ 9 วินาทีบวก overhead
ไม่ใช่รับประกันว่าจะเป็น 3 วินาที

5.6 /concurrent-fetch
---------------------

Helper fetch_safely(...) จัดการความล้มเหลวของแต่ละ API เอง และคืน tuple:

[โค้ด / แผนภาพ : python]
(data, fallback_was_used)
[จบโค้ด / แผนภาพ]

จากนั้นสร้าง coroutine 3 ตัวและรอพร้อมกัน:

[โค้ด / แผนภาพ : python]
cat_res, btc_res, joke_res = await asyncio.gather(
    cat_task, btc_task, joke_task
)
[จบโค้ด / แผนภาพ]

หากทั้งสาม timeout ใกล้ 3 วินาทีพร้อมกัน เวลารวมโดยแนวคิดจะใกล้ timeout ที่ช้าที่สุด
ไม่ใช่ 9 วินาที

[โค้ด / แผนภาพ : text]
Sequential: Cat ----> BTC ----> Joke ----> return
Concurrent: Cat  ----------------->
            BTC  -----------------> return เมื่อครบ
            Joke ----------------->
[จบโค้ด / แผนภาพ]

fallback_active = cat_fallback or btc_fallback or joke_fallback จึงเป็น true
ถ้ามีอย่างน้อยหนึ่งบริการใช้ mock

5.7 จุดสังเกตจากโค้ดจริง
------------------------

- HTTPException ถูก import แต่ไม่ได้ใช้
- API ภายนอกและค่าที่ตอบไม่แน่นอน จึงไม่ควรจำ expected output แบบตายตัว
- elapsed_seconds รวม network latency และ overhead จริง
- asyncio.gather() ช่วยเมื่อแต่ละงานเป็นอิสระต่อกัน
- การจับ error ภายใน fetch_safely() ป้องกัน API หนึ่งล้มแล้วทำให้ batch ทั้งหมดพัง

Part D — WebSocket Chat
=======================

6. HTTP กับ WebSocket ต่างกันอย่างไร
------------------------------------

- ประเด็น: รูปแบบ
  HTTP endpoint: request → response
  WebSocket: connection สองทางเปิดค้างไว้

- ประเด็น: เหมาะกับ
  HTTP endpoint: อ่าน/ส่งข้อมูลเป็นครั้ง ๆ
  WebSocket: chat, dashboard, game real-time

- ประเด็น: FastAPI decorator
  HTTP endpoint: @app.get, @app.post
  WebSocket: @app.websocket

- ประเด็น: รับข้อมูล
  HTTP endpoint: parameter/body
  WebSocket: receive_text() หรือ receive_json()

- ประเด็น: ส่งข้อมูล
  HTTP endpoint: return response
  WebSocket: send_text() หรือ send_json()

- ประเด็น: URL scheme
  HTTP endpoint: http://
  WebSocket: ws://

8.2 ConnectionManager
---------------------

[จบโค้ด / แผนภาพ]

เก็บ connection โดยใช้ student_id เป็น key:

[โค้ด / แผนภาพ : text]

  "6710301001": WebSocket-A,

------------------------

ผู้ส่งจะได้รับข้อความ broadcast กลับด้วย เพราะ connection ของผู้ส่งก็อยู่ใน dictionary

8.5 Flow เมื่อตัดการเชื่อมต่อ
-----------------------------

เมื่อ receive_text() เจอ WebSocketDisconnect:

1. ลบ student ID
2. broadcast ข้อความออกจากระบบให้คนที่ยังอยู่

8.6 ข้อจำกัดที่ควรรู้
---------------------

- ถ้าสอง browser ใช้ student_id ซ้ำ connection ใหม่จะเขียนทับค่าเดิมใน dictionary แต่
  connection เก่าอาจยังเปิดอยู่และไม่ได้อยู่ในชุด broadcast แล้ว
- broadcast() ไม่มี try/except ราย connection ถ้าการส่งไป connection หนึ่งล้ม
  อาจทำให้รอบ broadcast นั้นเกิด exception
- ข้อมูลอยู่ใน memory เท่านั้น restart server แล้วรายชื่อหาย
- ไม่มี authentication และไม่มีฐานข้อมูลประวัติข้อความ
- asyncio ถูก import แต่ไม่ได้เรียกใช้โดยตรงในไฟล์นี้

11.1 ขอบเขตสนามและ State
------------------------

Manager เก็บ dictionary สองชุด:

  เก็บอะไร: WebSocket ของทุก client รวม dashboard

- ตัวแปร: rockets

State ของจรวดหนึ่งลำ:

{
  "x": 400.0,

11.2 Endpoint
-------------

[โค้ด / แผนภาพ : text]
WebSocket /ws/{client_id}
[จบโค้ด / แผนภาพ]

ถ้า client_id == "DASHBOARD" server มองว่าเป็น dashboard และไม่สร้างจรวดให้ ถ้าเป็น ID
อื่นจะสร้าง state จรวด

11.3 Message protocol
---------------------

- type: INIT
  ทิศทาง: server → client ที่เพิ่งต่อ
  เกิดเมื่อ: connect สำเร็จ
  field สำคัญ: rockets, bounds

- type: SPAWN
  ทิศทาง: server → ทุก client
  เกิดเมื่อ: controller ใหม่เข้า
  field สำคัญ: id, rocket

- type: CONTROL
  ทิศทาง: controller → server
  เกิดเมื่อ: กดปุ่ม/ลูกศร
  field สำคัญ: action

- type: UPDATE
  ทิศทาง: server → ทุก client
  เกิดเมื่อ: server เปลี่ยน state
  field สำคัญ: id, rocket

- type: DESPAWN
  ทิศทาง: server → ทุก client
  เกิดเมื่อ: client disconnect
  field สำคัญ: id


ตัวอย่าง CONTROL:

[โค้ด / แผนภาพ : json]
{"type": "CONTROL", "action": "ROTATE_LEFT"}
[จบโค้ด / แผนภาพ]

ตัวอย่าง UPDATE:

[โค้ด / แผนภาพ : json]
{
  "type": "UPDATE",
  "id": "Rocket_101",
  "rocket": {"x": 408.0, "y": 300.0, "angle": 0, "color": "hsl(...)"}
}
[จบโค้ด / แผนภาพ]

11.4 การหมุน
------------

[โค้ด / แผนภาพ : python]
ROTATE_LEFT  -> angle = (angle - 15) % 360
ROTATE_RIGHT -> angle = (angle + 15) % 360
[จบโค้ด / แผนภาพ]

แต่ละครั้งหมุน 15 องศา และ % 360 ทำให้มุมอยู่ในรอบ 0–359

ตัวอย่าง:

[โค้ด / แผนภาพ : text]
เริ่ม 0°
กดซ้าย -> 345°
กดขวา -> 0°
[จบโค้ด / แผนภาพ]

11.5 การเคลื่อนที่ด้วย THRUST
-----------------------------

[โค้ด / แผนภาพ : python]
rad = math.radians(rocket["angle"])
new_x = rocket["x"] + 8 * math.cos(rad)
new_y = rocket["y"] + 8 * math.sin(rad)
[จบโค้ด / แผนภาพ]

- speed ต่อการกดหนึ่งครั้ง = 8 pixel
- 0° เพิ่ม x จึงเคลื่อนไปทางขวา
- 90° เพิ่ม y บน Canvas ซึ่งโดยพิกัดหน้าจอคือเคลื่อนลง
- 180° ลด x คือไปซ้าย
- 270° ลด y คือขึ้น

11.6 ล็อกขอบสนาม
----------------

[โค้ด / แผนภาพ : python]
x = max(20, min(780, new_x))
y = max(20, min(580, new_y))
[จบโค้ด / แผนภาพ]

Padding 20 pixel ป้องกันตัวจรวดหลุดจากสนาม 800×600

11.7 Broadcast และ disconnect
-----------------------------

broadcast() ใช้ list(self.connections.values()) เพื่อ snapshot ค่า และจับ exception ราย
connection แล้ว pass จึงทนต่อ connection ที่ส่งไม่สำเร็จได้ดีกว่า chat version แต่
connection เสียไม่ได้ถูกลบใน method นี้

เมื่อ controller หลุด:

1. ลบจาก connections
2. ลบจาก rockets
3. broadcast DESPAWN

ถ้า dashboard หลุด จะไม่มี rocket state ชื่อ DASHBOARD ให้ลบ แต่ server ยัง broadcast
DESPAWN ID DASHBOARD; dashboard อื่นที่รับ event นี้ก็เพียงพยายามลบ key ที่ปกติไม่มี

11.8 ข้อควรระวัง input
----------------------

โค้ดอ่าน data["type"] และ data["action"] ตรง ๆ ถ้า client ส่ง JSON ที่ไม่มี key เหล่านี้
อาจเกิด KeyError ซึ่งไม่ได้ถูกจับโดย except WebSocketDisconnect

16. Pitfalls และ Debug Checklist
--------------------------------

- อาการ: ModuleNotFoundError: fastapi
  สาเหตุที่เป็นไปได้: ยังไม่ได้ติดตั้ง
  วิธีตรวจ/แนวทาง: python -m pip install fastapi uvicorn

- อาการ: ModuleNotFoundError: httpx
  สาเหตุที่เป็นไปได้: ขาด HTTPX
  วิธีตรวจ/แนวทาง: python -m pip install httpx

- อาการ: Address already in use
  สาเหตุที่เป็นไปได้: port 8000/8001/8002/8088 ถูกใช้อยู่
  วิธีตรวจ/แนวทาง: หยุด process แล็บเดิมก่อน

- อาการ: /items/abc ได้ error
  สาเหตุที่เป็นไปได้: item_id ต้องเป็น int
  วิธีตรวจ/แนวทาง: ใช้ /items/123

- อาการ: /users ได้ validation error
  สาเหตุที่เป็นไปได้: ขาด username
  วิธีตรวจ/แนวทาง: เพิ่ม ?username=Alice

- อาการ: POST register ไม่ผ่าน
  สาเหตุที่เป็นไปได้: JSON ขาด field หรือ type ผิด
  วิธีตรวจ/แนวทาง: ตรวจ student_id, nickname, gpa

- อาการ: External API ได้ mock
  สาเหตุที่เป็นไปได้: upstream ล้ม/timeout/rate-limit
  วิธีตรวจ/แนวทาง: ดู log และ fallback_activated

- อาการ: Sequential บางครั้งเร็วกว่า/ช้ากว่าที่เดา
  สาเหตุที่เป็นไปได้: network latency จริงไม่คงที่
  วิธีตรวจ/แนวทาง: ทดลองหลายรอบและดู elapsed

- อาการ: Browser chat เปิดแต่ไม่มีข้อความ
  สาเหตุที่เป็นไปได้: central server ไม่เปิด/IP ผิด/port ถูก block
  วิธีตรวจ/แนวทาง: ตรวจ server 8088 และ URL WebSocket

- อาการ: client2.py แสดง :8000
  สาเหตุที่เป็นไปได้: ข้อความ HTML ไม่ตรง JavaScript
  วิธีตรวจ/แนวทาง: connection จริงใน JS ใช้ 8088

- อาการ: เปิด client สองตัวด้วย ID เดียว
  สาเหตุที่เป็นไปได้: dictionary key ถูกเขียนทับ
  วิธีตรวจ/แนวทาง: ใช้ ID ไม่ซ้ำ

- อาการ: Dashboard ไม่มีจรวด
  สาเหตุที่เป็นไปได้: Rocket server/controller ไม่เชื่อม
  วิธีตรวจ/แนวทาง: เปิด server → dashboard → controller

- อาการ: กดปุ่มแล้วไม่ขยับ
  สาเหตุที่เป็นไปได้: WebSocket ยังไม่ OPEN หรือ server ไม่ตอบ
  วิธีตรวจ/แนวทาง: ตรวจ browser console และ central server

- อาการ: จรวดเดิน “ลง” ที่ 90°
  สาเหตุที่เป็นไปได้: Canvas เพิ่มค่า y ลงด้านล่าง
  วิธีตรวจ/แนวทาง: เป็นระบบพิกัดหน้าจอปกติ

- อาการ: จรวดหยุดที่ขอบ
  สาเหตุที่เป็นไปได้: server clamp padding 20
  วิธีตรวจ/แนวทาง: เป็น behavior ที่ตั้งใจไว้

- อาการ: Dashboard เปิด port 8001 ไม่ได้
  สาเหตุที่เป็นไปได้: chat client.py หรือ app อื่นยังใช้ 8001
  วิธีตรวจ/แนวทาง: ปิดแล็บเดิมก่อน

- อาการ: Student เปิด port 8002 ไม่ได้
  สาเหตุที่เป็นไปได้: chat client2.py หรือ app อื่นยังใช้ 8002
  วิธีตรวจ/แนวทาง: ปิดแล็บเดิมก่อน

17. ตารางเปรียบเทียบแนวคิดสำคัญ
-------------------------------

17.1 def กับ async def
----------------------

- ประเด็น: object/function
  def: function ปกติ
  async def: coroutine function

- ประเด็น: ใช้ await ได้ไหม
  def: ไม่ได้
  async def: ได้

- ประเด็น: FastAPI execution
  def: ปกติรันใน thread pool
  async def: รันบน event loop

- ประเด็น: เหมาะกับ
  def: sync library/งานสั้น หรือจัดการ blocking อย่างเหมาะสม
  async def: งาน I/O ที่ library รองรับ async

- ประเด็น: ตัวอย่าง
  def: sync_delay()
  async def: async_delay()


17.2 time.sleep() กับ asyncio.sleep()
-------------------------------------

- คำสั่ง: time.sleep(3)
  ผลระหว่างรอ: block thread

- คำสั่ง: await asyncio.sleep(3)
  ผลระหว่างรอ: suspend coroutine และคืน control ให้ event loop


17.3 Sequential กับ Concurrent
------------------------------

- แบบ: Sequential
  เริ่มงานถัดไปเมื่อไร: งานก่อนหน้าจบ
  เวลาคร่าว ๆ: ผลรวมเวลารอ
  ตัวอย่าง: /sequential-fetch

- แบบ: Concurrent
  เริ่มงานถัดไปเมื่อไร: เริ่มหลายงานก่อนรอครบ
  เวลาคร่าว ๆ: ใกล้งานช้าที่สุด
  ตัวอย่าง: /concurrent-tasks, /concurrent-fetch


17.4 Text กับ JSON บน WebSocket
-------------------------------

- ระบบ: Chat
  รับ: receive_text()
  ส่ง: send_text()
  รูปแบบ: string

- ระบบ: Rocket
  รับ: receive_json()
  ส่ง: send_json()
  รูปแบบ: dictionary/JSON protocol


17.5 Chat Manager กับ Rocket Manager
------------------------------------

- ประเด็น: connection key
  Chat: student ID
  Rocket: rocket/client ID

- ประเด็น: state เพิ่มเติม
  Chat: ไม่มี
  Rocket: x, y, angle, color

- ประเด็น: broadcast
  Chat: text
  Rocket: JSON event

- ประเด็น: Dashboard พิเศษ
  Chat: ไม่มี
  Rocket: ID DASHBOARD

- ประเด็น: send error handling
  Chat: ไม่มี try/except ราย connection
  Rocket: catch exception แล้ว pass

4. ตรวจว่า UPDATE ของ ID หนึ่งไม่แก้ state อีก ID

Lab 10 — ออกแบบ Message ใหม่บนกระดาษ
------------------------------------

ไม่ต้องแก้โค้ด ออกแบบ event RESET เพื่อย้ายจรวดกลับ (400,300,0) ตอบว่า:

- JSON จาก controller ควรหน้าตาอย่างไร
- server ต้องตรวจที่ส่วนไหน
- server ควร broadcast event ใดหลัง reset
- dashboard ต้องแก้หรือไม่ หากได้รับ UPDATE รูปแบบเดิม

คำตอบที่สมเหตุผลคือส่ง {"type":"CONTROL","action":"RESET"} ให้ server เพิ่ม branch แล้ว
broadcast UPDATE; dashboard ไม่ต้องเพิ่ม protocol ใหม่

2. 🎯 Use case — เรียนแล้วใช้ทำอะไรได้
-------------------------------------

หลังอ่านบทนี้ ใบจะสามารถ:

- เขียน async client ที่ส่ง HTTP request หลายสายพร้อมกัน
- รักษาลำดับขั้นตอนภายใน workflow หนึ่งสาย
- ใช้ client เดียวซ้ำหลาย request เพื่อประหยัด overhead

- ตรวจ HTTP error ด้วย raise_for_status()
- อธิบายความแตกต่างระหว่าง sequential และ concurrent ได้

แนวคิดเดียวกันนำไปใช้กับงานจริงได้ เช่น:

- Robot แต่ละตัวต้องทำขั้นตอน pick -> inspect -> pack ตามลำดับ แต่ Robot
  หลายตัวทำงานพร้อมกัน
- ลูกค้าแต่ละคนต้องผ่าน validate -> charge -> issue receipt ตามลำดับ
  แต่รับลูกค้าหลายคนพร้อมกัน
- ดาวน์โหลดไฟล์แต่ละชุดตามลำดับภายในชุด แต่ดาวน์โหลดหลายชุดพร้อมกัน

3. คำศัพท์สำคัญ
---------------

- คำศัพท์: Client
  ความหมายแบบง่าย: โปรแกรมที่ส่งคำขอ
  ตัวอย่างใน robots.py: robots.py

- คำศัพท์: Server
  ความหมายแบบง่าย: ระบบที่รับคำสั่งและตอบกลับ
  ตัวอย่างใน robots.py: 172.16.2.117:8088

- คำศัพท์: HTTP request
  ความหมายแบบง่าย: คำขอที่ Client ส่งไป
  ตัวอย่างใน robots.py: client.post(...)

- คำศัพท์: HTTP response
  ความหมายแบบง่าย: คำตอบที่ Server ส่งกลับ
  ตัวอย่างใน robots.py: ตัวแปร response

- คำศัพท์: Endpoint
  ความหมายแบบง่าย: HTTP method + URL path ของงานหนึ่งอย่าง
  ตัวอย่างใน robots.py: POST /student/.../reset

- คำศัพท์: Payload
  ความหมายแบบง่าย: ข้อมูลที่แนบไปกับ request
  ตัวอย่างใน robots.py: {"part": "A"}

- คำศัพท์: JSON
  ความหมายแบบง่าย: รูปแบบข้อมูล key-value
  ตัวอย่างใน robots.py: {"part": part}

- คำศัพท์: Coroutine function
  ความหมายแบบง่าย: ฟังก์ชันที่ประกาศด้วย async def
  ตัวอย่างใน robots.py: grab_part()

- คำศัพท์: Coroutine object
  ความหมายแบบง่าย: สิ่งที่ได้เมื่อเรียก async function แต่ยังไม่ await
  ตัวอย่างใน robots.py: run_robot_task(client, robot_id)

- คำศัพท์: Awaitable
  ความหมายแบบง่าย: สิ่งที่ใช้กับ await ได้
  ตัวอย่างใน robots.py: coroutine และ Task

- คำศัพท์: await
  ความหมายแบบง่าย: รอผลโดยคืน control ให้ Event Loop ระหว่างรอ I/O
  ตัวอย่างใน robots.py: await client.post(...)

- คำศัพท์: Event Loop
  ความหมายแบบง่าย: ตัวจัดคิวและสลับงาน async
  ตัวอย่างใน robots.py: เริ่มโดย asyncio.run(main())

- คำศัพท์: Sequential
  ความหมายแบบง่าย: ทำตามลำดับทีละขั้น
  ตัวอย่างใน robots.py: A -> B -> C ของ Robot เดียว

- คำศัพท์: Concurrent
  ความหมายแบบง่าย: หลายงานคืบหน้าเหลื่อมกันในเวลาเดียวกัน
  ตัวอย่างใน robots.py: Robot 4 ตัวผ่าน gather()

- คำศัพท์: Parallel
  ความหมายแบบง่าย: ทำงานจริงในเวลาเดียวกันบนหลายหน่วยประมวลผล
  ตัวอย่างใน robots.py: ไม่ใช่ประเด็นที่โค้ดนี้รับประกัน

- คำศัพท์: I/O-bound
  ความหมายแบบง่าย: งานที่ใช้เวลาส่วนใหญ่รอภายนอก
  ตัวอย่างใน robots.py: รอ Network/Server ตอบ

- คำศัพท์: Timeout
  ความหมายแบบง่าย: เวลารอสูงสุด
  ตัวอย่างใน robots.py: timeout=10.0

- คำศัพท์: Exception
  ความหมายแบบง่าย: ข้อผิดพลาดที่ขัดจังหวะ flow ปกติ
  ตัวอย่างใน robots.py: httpx.HTTPError


Concurrent ไม่เท่ากับ Parallel
------------------------------

ในโปรแกรมนี้ concurrency เกิดเพราะเมื่อ Robot หนึ่งกำลังรอ HTTP response Event Loop
สามารถสลับไปส่งหรือรอ request ของ Robot อื่นได้

[โค้ด / แผนภาพ : text]
Concurrency = หลายงานคืบหน้าในช่วงเวลาเดียวกัน
Parallelism = หลายงานประมวลผลพร้อมกันจริงบนหลาย core/thread/process
[จบโค้ด / แผนภาพ]

asyncio หนึ่ง Event Loop ก็สร้าง concurrency สำหรับงาน I/O ได้ โดยไม่จำเป็นต้องสร้าง 4
threads หรือ 4 processes

7.2 อธิบายทีละบรรทัด
--------------------

[โค้ด / แผนภาพ : python]

- await รอ HTTP response แบบไม่ block Event Loop ทั้งหมด

[โค้ด / แผนภาพ : python]
response.raise_for_status()
[จบโค้ด / แผนภาพ]

- ถ้า status สำเร็จ โปรแกรมทำงานต่อ
- ถ้าเป็น HTTP error เช่น 4xx หรือ 5xx จะเกิด httpx.HTTPStatusError
- error นี้เป็น subclass ในกลุ่ม httpx.HTTPError จึงถูกจับที่ท้ายไฟล์ได้

- แปลง JSON response เป็น Python object เช่น dictionary/list ตาม body จริง
- ถ้า body ไม่ใช่ JSON ที่ถูกต้อง อาจเกิด ValueError
- ValueError ถูกจับใน if __name__ == "__main__"

- เปรียบเทียบพฤติกรรมแต่ละรอบง่ายขึ้น

9. run_robot_task(client, robot_id)
-----------------------------------

โค้ด:

[โค้ด / แผนภาพ : python]
async def run_robot_task(client: httpx.AsyncClient, robot_id: str):
    for part in PARTS:
        await grab_part(client, robot_id, part)
[จบโค้ด / แผนภาพ]

ในไฟล์จริง บรรทัด await grab_part(...) เยื้องมากกว่าระดับมาตรฐานเล็กน้อย แต่ยังอยู่ใน
block ของ for และ Python ยอมรับได้ ตราบใดที่ indentation ภายใน block สอดคล้องกัน

9.1 หน้าที่
------------

ดูแล workflow ของ Robot หนึ่งตัว ตั้งแต่ A ถึง C

ตัวอย่าง robot_3:

[โค้ด / แผนภาพ : text]
run_robot_task(client, "robot_3")
       |
       v
POST grab A -> await จนสำเร็จ
       |
       v
POST grab B -> await จนสำเร็จ
       |
       v
POST grab C -> await จนสำเร็จ
       |
       v
return None โดยปริยาย
[จบโค้ด / แผนภาพ]

9.2 ทำไม loop นี้เป็น Sequential
--------------------------------

เพราะมี await อยู่ในแต่ละรอบ:

[โค้ด / แผนภาพ : python]
for part in PARTS:
    await grab_part(...)
[จบโค้ด / แผนภาพ]

Python จะไม่เลื่อนไป part ถัดไปของ Robot ตัวเดิมจน grab_part() รอบปัจจุบันจบ

จึงรับประกันลำดับในฝั่ง Client ว่า:

[โค้ด / แผนภาพ : text]
A response สำเร็จ -> จึงส่ง B
B response สำเร็จ -> จึงส่ง C
[จบโค้ด / แผนภาพ]

9.3 ถ้า A fail จะเกิดอะไร
-------------------------

หาก grab_part(..., "A") โยน exception:

- loop ของ Robot ตัวนั้นหยุดทันที
- B และ C ของ Robot ตัวนั้นไม่ถูกส่งจาก coroutine นี้
- exception ไหลออกจาก run_robot_task() ไปยัง gather()
- main() ไม่ได้จับภายใน จึงไหลไปยัง error handler ระดับบน

พฤติกรรมของ Robot งานอื่นเมื่อ gather() เจอ exception ต้องคิดอย่างระวัง: ไม่ควรสรุปง่าย
ๆ ว่าทุกงานจะถูก rollback หรือ cancel บน Server เพราะ HTTP request
ที่ส่งออกไปแล้วอาจทำงานต่อ

9.4 Return value ปัจจุบัน
-------------------------

ฟังก์ชันไม่มี return ชัดเจน จึงเท่ากับ:

[โค้ด / แผนภาพ : python]
return None
[จบโค้ด / แผนภาพ]

ถ้าเก็บผลจาก gather จะได้แนวคิดเป็น:

[โค้ด / แผนภาพ : python]
[None, None, None, None]
[จบโค้ด / แผนภาพ]

เมื่อทุก Robot สำเร็จ แต่โค้ดปัจจุบันไม่ได้เก็บ list นี้

10. main()
------------

โค้ดสำคัญ:

[โค้ด / แผนภาพ : python]
async def main():
    async with httpx.AsyncClient(base_url=BASE_URL, timeout=10.0) as client:
        print("Resetting Factory...")
        await reset_factory(client)

        start_time = time.time()
        print("Starting Async Robot Operation...")

        robot_tasks = [run_robot_task(client, robot_id) for robot_id in ROBOTS]
        await asyncio.gather(*robot_tasks)

        elapsed_time = time.time() - start_time
        print(f"Finished all tasks in {elapsed_time:.2f} seconds.")
[จบโค้ด / แผนภาพ]

await reset_factory(client)
[จบโค้ด / แผนภาพ]

จุดนี้เป็น sequential gate: ต้อง reset สำเร็จก่อนจึงเริ่ม Robot ทั้ง 4 ตัว

10.3 เริ่มจับเวลา
-----------------

[โค้ด / แผนภาพ : python]
start_time = time.time()
[จบโค้ด / แผนภาพ]

เวลาที่วัดครอบคลุมตั้งแต่ก่อนสร้าง/รัน Robot coroutines จน gather() รอครบ แต่ไม่รวม
reset และไม่รวมเวลาสร้าง/ปิด client ทั้งหมด

10.4 สร้าง coroutine 4 ตัว
--------------------------

[โค้ด / แผนภาพ : python]
robot_tasks = [run_robot_task(client, robot_id) for robot_id in ROBOTS]
[จบโค้ด / แผนภาพ]

ค่าทางแนวคิดใน list:

[โค้ด / แผนภาพ : text]
run_robot_task(client, "robot_1")
run_robot_task(client, "robot_2")
run_robot_task(client, "robot_3")
run_robot_task(client, "robot_4")
[จบโค้ด / แผนภาพ]

ชื่อตัวแปร robot_tasks อาจทำให้เข้าใจว่าเป็น asyncio.Task objects แล้ว แต่จริง ๆ list
comprehension นี้ได้ coroutine objects เพราะไม่ได้เรียก asyncio.create_task() โดยตรง

asyncio.gather() รับ coroutine เหล่านี้ได้ และจัด schedule ให้ทำงาน concurrent

10.5 แตก list ด้วย *
--------------------

[โค้ด / แผนภาพ : python]
await asyncio.gather(*robot_tasks)
[จบโค้ด / แผนภาพ]

ถ้าไม่ใส่ * จะเหมือนส่ง list เป็น argument เดียว ซึ่งไม่ใช่ awaitable ที่ gather()
ต้องการในรูปแบบนี้

เครื่องหมาย * แปลงจาก:

[โค้ด / แผนภาพ : python]
[coro1, coro2, coro3, coro4]
[จบโค้ด / แผนภาพ]

เป็นการส่ง argument:

[โค้ด / แผนภาพ : python]
asyncio.gather(coro1, coro2, coro3, coro4)
[จบโค้ด / แผนภาพ]

10.6 รอครบทุก Robot
-------------------

await asyncio.gather(...) ไม่จบใน success path จน coroutine ของ Robot ทั้ง 4 ตัวเสร็จ
ดังนั้นเมื่อถึงบรรทัดคำนวณเวลา ตาม flow ปกติ request grab ทั้ง 12 ครั้งสำเร็จครบแล้ว

10.7 คำนวณและแสดงเวลา

[จบโค้ด / แผนภาพ]

.2f แสดงทศนิยม 2 ตำแหน่ง เช่น:

[โค้ด / แผนภาพ : text]

[จบโค้ด / แผนภาพ]

Part D — หัวใจของ Concurrency
=============================

12. Sequential ภายใน Robot แต่ละตัว
-----------------------------------

แต่ละ Robot มี dependency chain:

[โค้ด / แผนภาพ : text]
robot_1: A --------> B --------> C
robot_2: A --------> B --------> C
robot_3: A --------> B --------> C
robot_4: A --------> B --------> C
[จบโค้ด / แผนภาพ]

ในแต่ละแถว ลูกศรหมายถึง “ต้องรอ response สำเร็จก่อน”

เหตุผลที่ต้อง sequential อาจเป็นกฎของ Server/โรงงาน เช่น Robot
ต้องประกอบชิ้นส่วนตามขั้นตอน แม้ robots.py ไม่ได้อธิบายเหตุผลทางธุรกิจเพิ่มเติม
แต่โค้ดยืนยันลำดับชัดเจน

รูปแบบที่ถูก
------------

[โค้ด / แผนภาพ : python]
for part in PARTS:
    await grab_part(client, robot_id, part)
[จบโค้ด / แผนภาพ]

รูปแบบที่เปลี่ยน semantics
--------------------------

[โค้ด / แผนภาพ : python]
await asyncio.gather(
    *(grab_part(client, robot_id, part) for part in PARTS)
)
[จบโค้ด / แผนภาพ]

รูปแบบหลังจะพยายามให้ A, B, C ของ Robot เดียวกัน concurrent ซึ่งไม่ตรงกับ “Sequential
inside single robot” ของไฟล์ปัจจุบัน

----------------------------------------------------------------

13. Concurrent ระหว่าง Robot 4 ตัว
----------------------------------

Robot คนละตัวเป็น workflow แยกกัน จึงส่งเข้า gather() พร้อมกันได้:

[โค้ด / แผนภาพ : text]
เวลา --->

robot_1: [grab A] [grab B] [grab C]
robot_2: [grab A]----[grab B]--[grab C]
robot_3: [grab A]--[grab B]----[grab C]
robot_4: [grab A] [grab B]-----[grab C]
[จบโค้ด / แผนภาพ]

ความยาวกล่องเป็นภาพแนวคิดเท่านั้น เพราะไฟล์ไม่ได้บอก delay จริง

Event Loop ทำงานโดยประมาณ:

[โค้ด / แผนภาพ : text]
1. เริ่ม coroutine robot_1 -> ส่ง A -> รอ network
2. สลับไป robot_2       -> ส่ง A -> รอ network
3. สลับไป robot_3       -> ส่ง A -> รอ network
4. สลับไป robot_4       -> ส่ง A -> รอ network
5. response ของตัวใดมาก่อน ตัวนั้นไปส่ง B ของตัวเอง
6. ทำต่อจนแต่ละตัวครบ C
7. gather จบเมื่อครบทั้ง 4 ตัว
[จบโค้ด / แผนภาพ]

คำว่า “พร้อมกัน” ในบทเรียนนี้ควรอธิบายอย่างแม่นยำว่า request มีโอกาส คืบหน้าเหลื่อมกัน
ไม่ได้แปลว่าทุกบรรทัด Python ทำใน nanosecond เดียวกัน

----------------------------------------------------------------

14. เจาะลึก asyncio.gather()
----------------------------

บรรทัดหลัก:

[โค้ด / แผนภาพ : python]
await asyncio.gather(*robot_tasks)
[จบโค้ด / แผนภาพ]

14.1 gather() ทำอะไรใน success path
-----------------------------------

- รับ awaitable หลายตัว
- schedule coroutine ให้ทำงาน concurrent
- รอจนทุกตัวสำเร็จ
- คืนผลตามลำดับ input

14.2 ลำดับเสร็จ vs ลำดับผล
--------------------------

สมมติ Robot เสร็จจริงตามลำดับ:

[โค้ด / แผนภาพ : text]
robot_3 -> robot_1 -> robot_4 -> robot_2
[จบโค้ด / แผนภาพ]

ถ้าเก็บผล:

[โค้ด / แผนภาพ : python]
results = await asyncio.gather(*robot_tasks)
[จบโค้ด / แผนภาพ]

results ยังเรียงตาม input ROBOTS:

[โค้ด / แผนภาพ : text]
result ของ robot_1
result ของ robot_2
result ของ robot_3
result ของ robot_4
[จบโค้ด / แผนภาพ]

แต่ในโค้ดปัจจุบันแต่ละ coroutine return None

14.3 ถ้า Robot หนึ่งเกิด exception
----------------------------------

ค่า default ของ gather() คือไม่ใช้ return_exceptions=True ดังนั้น exception
จะถูกส่งออกมายังผู้ await

สิ่งที่ต้องระวัง:

- โปรแกรมจะไม่ถึงข้อความ Finished all tasks... ใน flow error นั้น
- error จะถูกส่งขึ้นไปยัง try/except ถ้าเป็นชนิดที่จับไว้
- อย่าสมมติว่า HTTP POST ที่ Server รับไปแล้วถูก rollback
- อย่าสมมติว่าการหยุดรอของ Client ทำให้สถานะ Server ย้อนกลับ

14.4 ทำไมไม่จำเป็นต้อง create_task() ก่อน
-----------------------------------------

gather() รับ coroutine objects ได้โดยตรงและจัด schedule ให้ จึงใช้รูปแบบนี้ได้:

[โค้ด / แผนภาพ : python]
coroutines = [run_robot_task(...) for ...]
await asyncio.gather(*coroutines)
[จบโค้ด / แผนภาพ]

ถ้าต้องการตั้งชื่อ Task ตรวจ .done() หรือ cancel เป็นรายตัว จึงค่อยพิจารณา
asyncio.create_task()

15. เจาะลึก httpx.AsyncClient
-----------------------------

15.1 ทำไมไม่ใช้ httpx.Client
----------------------------

httpx.AsyncClient มี method แบบ awaitable:

[โค้ด / แผนภาพ : python]
response = await client.post(...)
[จบโค้ด / แผนภาพ]

จึงเปิดโอกาสให้ Event Loop ไปดู Robot อื่นระหว่างรอ I/O

ถ้าใช้ synchronous client ใน Event Loop การรอ network อาจ block thread และลดประโยชน์ของ
concurrency

15.2 ทำไมใช้ Client เดียวร่วมกัน
--------------------------------

main() สร้าง client ครั้งเดียวแล้วส่ง reference เดิมให้ทุกฟังก์ชัน

ข้อดี:

- reuse connection pool
- ลด overhead จากการสร้าง client ใหม่ 13 ครั้ง
- รวม base_url และ timeout ไว้จุดเดียว
- ปิด resource อย่างเป็นระบบด้วย async with
- รูปแบบ function แยกหน้าที่ชัดเจนและทดสอบด้วย transport จำลองได้ง่ายขึ้น

15.3 base_url ต่อกับ relative path
----------------------------------

[โค้ด / แผนภาพ : python]
base_url = "http://172.16.2.117:8088"
path = "/student/6710301033/reset"
[จบโค้ด / แผนภาพ]

ผล URL ที่ต้องการ:

[โค้ด / แผนภาพ : text]
http://172.16.2.117:8088/student/6710301033/reset
[จบโค้ด / แผนภาพ]

15.4 json=payload
-----------------

[โค้ด / แผนภาพ : python]
await client.post(url_path, json={"part": "A"})
[จบโค้ด / แผนภาพ]

json= ต่างจาก data= เพราะบอก HTTPX ว่าต้องส่งข้อมูลแบบ JSON และ serialize Python
dictionary ให้

15.5 Timeout 10 วินาที
----------------------

[โค้ด / แผนภาพ : python]
timeout=10.0
[จบโค้ด / แผนภาพ]

เป็นค่า timeout config ของ HTTPX สำหรับ request ผ่าน client นี้
ไม่ได้แปลว่าโปรแกรมทั้งชุดมีเวลารวมสูงสุด 10 วินาที

เหตุผล:

- Robot หนึ่งตัวมี 3 request sequential
- แต่ละ request อาจใช้เวลาของตนเอง
- reset ก็เป็นอีก request

ดังนั้น “10 วินาที” ไม่ควรถูกตีความว่า elapsed ทั้งโรงงานต้องต่ำกว่า 10 วินาทีเสมอ

15.6 raise_for_status()
-----------------------

HTTP request “ได้รับ response” ไม่ได้แปลว่า “สำเร็จ” เพราะ Server อาจตอบ 4xx/5xx

[โค้ด / แผนภาพ : python]
response.raise_for_status()
[จบโค้ด / แผนภาพ]

ทำหน้าที่เปลี่ยน HTTP error status เป็น exception เพื่อหยุด success flow

16. Timing Model
----------------

ใน robots.py ไม่มีตาราง delay ของ A, B, C หรือ Robot แต่ละตัว จึงคำนวณตัวเลขตายตัวไม่ได้

ให้กำหนดเชิงสัญลักษณ์:

[โค้ด / แผนภาพ : text]
T(r, A) = เวลาที่ Robot r ใช้ request A
T(r, B) = เวลาที่ Robot r ใช้ request B
T(r, C) = เวลาที่ Robot r ใช้ request C
[จบโค้ด / แผนภาพ]

เพราะภายใน Robot เป็น sequential:

[โค้ด / แผนภาพ : text]
เวลาของ robot_r ≈ T(r,A) + T(r,B) + T(r,C)
[จบโค้ด / แผนภาพ]

เพราะ Robot 4 ตัว concurrent:

[โค้ด / แผนภาพ : text]
เวลาช่วง Robot ทั้งหมด
≈ max(
    เวลาของ robot_1,
    เวลาของ robot_2,
    เวลาของ robot_3,
    เวลาของ robot_4
  )
+ scheduling/network overhead
[จบโค้ด / แผนภาพ]

ไม่ใช่โดยทั่วไป:

[โค้ด / แผนภาพ : text]
ผลรวมเวลาของ request ทั้ง 12 ครั้ง
[จบโค้ด / แผนภาพ]

กรณีสมมติเพื่อฝึกคิด
--------------------

ถ้าทุก grab ใช้ 1 วินาทีเท่ากัน:

[โค้ด / แผนภาพ : text]
Robot หนึ่งตัว = 1 + 1 + 1 = 3 วินาที
Robot สี่ตัว concurrent = ประมาณ 3 วินาที + overhead
Robot สี่ตัว sequential = ประมาณ 12 วินาที + overhead
[จบโค้ด / แผนภาพ]

ตัวเลขนี้เป็น โจทย์สมมติ ไม่ใช่ delay จริงจาก Server

ช่วงที่ถูกจับเวลา
-----------------

[โค้ด / แผนภาพ : text]
สร้าง Client
Reset Factory            <- ไม่รวมใน elapsed_time
ตั้ง start_time          <- เริ่มจับตรงนี้
Robot 1-4 ทำงาน
กather รอครบ
คำนวณ elapsed_time       <- หยุดเชิงตรรกะตรงนี้
ปิด Client               <- ไม่รวมหลังคำนวณ
[จบโค้ด / แผนภาพ]

ไม่รับประกันลำดับข้าม Robot เช่น:

[โค้ด / แผนภาพ : text]

[จบโค้ด / แผนภาพ]

เพราะ Robot ทำ concurrent และขึ้นกับ Network/Server scheduling

21. Network Caveats — ข้อควรระวังเรื่องเครือข่าย
------------------------------------------------

172.16.2.117 เป็น private IPv4 address โดยทั่วไปเข้าถึงได้เฉพาะเครือข่ายภายในที่ route
ถึงเครื่องนั้น เช่น Wi-Fi/LAN ห้องเรียนหรือ VPN ที่กำหนด

172.16.2.117 ไม่ใช่ 127.0.0.1
-----------------------------

[โค้ด / แผนภาพ : text]
127.0.0.1     = เครื่องที่กำลังรัน Python เอง
172.16.2.117  = เครื่องอื่น/Server ใน private network ตามโค้ด
[จบโค้ด / แผนภาพ]

การเปิด local server ที่ 127.0.0.1:8088 จะไม่ทำให้ client ปัจจุบันส่งไป local เพราะ
BASE_URL ยังชี้ 172.16.2.117:8088

Port 8088
------------

URL ต้องมี port ตรงกับ Server:

[โค้ด / แผนภาพ : text]
http://172.16.2.117:8088
[จบโค้ด / แผนภาพ]

ถ้าตัด :8088 browser/client จะใช้ default port ของ HTTP ซึ่งเป็นคนละปลายทาง

Timeout ไม่เท่ากับ Server rollback
----------------------------------

ถ้า Client timeout ขณะ POST:

[โค้ด / แผนภาพ : text]
Client อาจหยุดรอ
แต่ Server อาจรับคำสั่งแล้วและทำงานต่อ
[จบโค้ด / แผนภาพ]

ดังนั้น:

[โค้ด / แผนภาพ : text]
Timeout != ยืนยันว่า Robot state ไม่เปลี่ยน
[จบโค้ด / แผนภาพ]

หากต้องรู้สถานะจริง ต้องใช้ endpoint ตรวจสถานะหรือกลไก reset ตาม API ที่ Server รองรับ
แต่ robots.py ไม่มี status endpoint จึงไม่ควรเดา URL

ห้ามเปลี่ยน BASE_URL หรือ Student ID โดยเดา
-------------------------------------------

โค้ดปัจจุบันกำหนดชัดเจน:

[โค้ด / แผนภาพ : python]
BASE_URL = "http://172.16.2.117:8088"

[จบโค้ด / แผนภาพ]

ก่อนส่งงานให้รักษาค่าตาม requirement อาจารย์ ถ้าจะทดลอง Server
อื่นควรทำอย่างมีขอบเขตและคืนค่าก่อนส่ง

Part G — Pitfalls และ Debugging
===============================

22. Pitfalls ที่พบบ่อย
----------------------

22.1 ลืม await
--------------

ผิด:

[โค้ด / แผนภาพ : python]
client.post(url_path, json=payload)
[จบโค้ด / แผนภาพ]

จะได้ coroutine/awaitable ของ HTTPX แต่ request อาจไม่ถูกดำเนินการตามที่คาด และอาจมี
warning

ถูก:

[โค้ด / แผนภาพ : python]
await client.post(url_path, json=payload)
[จบโค้ด / แผนภาพ]

22.2 ทำ A, B, C concurrent ภายใน Robot
--------------------------------------

ถ้าใช้ gather กับ parts ของ Robot เดียว จะทำลายลำดับ sequential ของโจทย์

22.3 ทำ Robot ทั้ง 4 sequential
-------------------------------

รูปแบบนี้ช้ากว่าและไม่ตรงจุดประสงค์:

[โค้ด / แผนภาพ : python]
for robot_id in ROBOTS:
    await run_robot_task(client, robot_id)
[จบโค้ด / แผนภาพ]

เพราะ Robot ถัดไปเริ่มหลังตัวก่อนครบ A, B, C แล้ว

22.4 ส่ง list เข้า gather() โดยไม่แตก *
---------------------------------------

ผิด:

[โค้ด / แผนภาพ : python]
await asyncio.gather(robot_tasks)
[จบโค้ด / แผนภาพ]

ถูก:

[โค้ด / แผนภาพ : python]
await asyncio.gather(*robot_tasks)
[จบโค้ด / แผนภาพ]

22.5 ใช้ time.sleep() ใน coroutine
----------------------------------

time.sleep() block Event Loop thread ถ้าต้องรอใน client logic ให้ใช้ await
asyncio.sleep() แต่ในโปรแกรมนี้การรอหลักเกิดใน await client.post() อยู่แล้ว

22.6 ลืม raise_for_status()
---------------------------

การได้ response 404/500 ก็ยังเป็น response object หากไม่ตรวจ status อาจประกาศ success
ผิด

22.7 เข้าใจ local return เป็น Server response
---------------------------------------------

grab_part() คืน:

[โค้ด / แผนภาพ : python]
{"robot": ..., "part": ..., "status": "success"}
[จบโค้ด / แผนภาพ]

แต่ dictionary นี้สร้างใน Client ไม่ได้อ่านจาก response.json()

22.8 คิดว่า timeout 10 วินาทีครอบทั้งโปรแกรม
--------------------------------------------

ค่าของ HTTPX ใช้กับ request operations ตาม config ไม่ใช่ global deadline ของ Robot
workflow ทั้งหมด

22.9 คิดว่า robot_tasks เป็น Task object แล้ว
---------------------------------------------

ค่าปัจจุบันเป็น coroutine objects จน gather() schedule ให้ ถ้าต้องการ method เช่น
.done() ต้องสร้าง Task จริงก่อน

22.10 คิดว่า gather() ทำให้ลำดับ A/B/C หาย
------------------------------------------

gather() อยู่ระดับ Robot ส่วน loop ที่ await ทีละ part ยังรักษาลำดับของแต่ละ Robot

22.11 ใช้ synchronous HTTP client ใน async flow
-----------------------------------------------

อาจ block Event Loop ทำให้ Robot อื่นไม่คืบหน้าระหว่างรอ network

22.12 ทดสอบ live ซ้ำโดยไม่รู้ผลข้างเคียง
----------------------------------------

โปรแกรม reset state แล้วส่ง POST จำนวนมาก การรันซ้ำอาจชนกับการดูผลหรือการทดลอง process
อื่นของ Student ID เดียวกัน

23. Debug Checklist
-------------------

- อาการ: ModuleNotFoundError: httpx
  สาเหตุที่เป็นไปได้: ยังไม่ติดตั้ง package ใน Python environment นี้
  วิธีตรวจ: python -m pip install httpx

- อาการ: ConnectError
  สาเหตุที่เป็นไปได้: Server ปิด, IP ผิด, อยู่คนละ network
  วิธีตรวจ: ตรวจ network และ BASE_URL

- อาการ: ConnectTimeout
  สาเหตุที่เป็นไปได้: ต่อปลายทางไม่ทัน
  วิธีตรวจ: ตรวจ Wi-Fi/VPN/firewall/Server

- อาการ: ReadTimeout
  สาเหตุที่เป็นไปได้: ต่อได้แต่ Server ตอบช้าเกิน config
  วิธีตรวจ: ตรวจ Server load และ timeout

- อาการ: HTTP 404
  สาเหตุที่เป็นไปได้: path, Student ID หรือ Robot ID ไม่ตรง API
  วิธีตรวจ: เปรียบเทียบ endpoint ทีละตัวอักษร

- อาการ: HTTP 4xx
  สาเหตุที่เป็นไปได้: payload หรือ state ไม่ถูกต้อง
  วิธีตรวจ: ตรวจ {"part": "A/B/C"} และ error body

- อาการ: HTTP 5xx
  สาเหตุที่เป็นไปได้: Server เกิดปัญหา
  วิธีตรวจ: ดู Server log/แจ้งผู้ดูแล

- อาการ: ValueError หลัง reset
  สาเหตุที่เป็นไปได้: reset response ไม่ใช่ JSON ที่ parse ได้
  วิธีตรวจ: ตรวจ response จริงด้วยเครื่องมือที่ได้รับอนุญาต

- อาการ: เห็นแค่ 3 บรรทัด
  สาเหตุที่เป็นไปได้: โค้ดไม่ได้ print ราย part
  วิธีตรวจ: เป็น behavior ปัจจุบัน ไม่จำเป็นต้องเป็น bug

- อาการ: เวลาไม่คงที่
  สาเหตุที่เป็นไปได้: Network และ Server scheduling เปลี่ยน
  วิธีตรวจ: ดูแนวโน้มหลายรอบ ไม่ยึดเลขเดียว

- อาการ: บาง Robot หยุดก่อน C
  สาเหตุที่เป็นไปได้: request ก่อนหน้าเกิด exception
  วิธีตรวจ: อ่าน Error: และ Server log

- อาการ: Local server เปิดแต่ยังต่อไม่ได้
  สาเหตุที่เป็นไปได้: code ชี้ private IP
  วิธีตรวจ: ตรวจ BASE_URL

Part I — คำถามแนวสอบ
====================

31. คำถามพร้อมคำตอบสั้น
-----------------------

31.1 async def คืออะไร
----------------------

ใช้ประกาศ coroutine function ซึ่งสามารถใช้ await ภายในและทำงานกับ Event Loop ได้

31.2 await ทำอะไร
-----------------

รอ awaitable ให้เสร็จ พร้อมเปิดโอกาสให้ Event Loop ไปจัดการงาน async อื่นระหว่างรอ I/O

31.3 ทำไม grab_part() เหมาะกับ async
------------------------------------

เพราะส่ง HTTP request ซึ่งเป็นงาน I/O-bound เวลาส่วนใหญ่คือการรอ Network/Server

31.4 ทำไม A, B, C ต้อง sequential
---------------------------------

เพราะ for part in PARTS มี await grab_part(...) ในแต่ละรอบ จึงไม่เริ่ม part
ถัดไปจนรอบปัจจุบันสำเร็จ

31.5 ทำไม Robot 4 ตัว concurrent
--------------------------------

เพราะสร้าง coroutine 4 ตัวและส่งทั้งหมดให้ asyncio.gather()

31.6 gather() รออะไร
--------------------

ใน success path รอ awaitable ทั้งหมดให้เสร็จ และคืนผลตามลำดับ input

31.7 robot_tasks เป็น Task object หรือไม่
-----------------------------------------

ในโค้ดปัจจุบันเป็น list ของ coroutine objects ก่อนส่งให้ gather() ไม่ได้สร้างด้วย
asyncio.create_task() โดยตรง

31.8 *robot_tasks ทำอะไร
------------------------

แตกสมาชิกใน list ให้เป็น positional arguments หลายตัวของ gather()

31.9 ทำไม reuse AsyncClient
---------------------------

ใช้ connection pool ร่วมกัน ลด overhead รวม config ไว้จุดเดียว และปิด resource ด้วย
async with

31.10 base_url ทำอะไร
---------------------

39. สรุปสุดท้าย
---------------

จำ 8 ข้อนี้ให้ได้:

1. robots.py เป็น async HTTP client ที่คุยกับ http://172.16.2.117:8088
2. Student ID ปัจจุบันคือ 6710301033
3. โปรแกรม reset ก่อนเริ่ม และเวลา reset ไม่รวมใน elapsed time
4. Robot แต่ละตัวหยิบ A -> B -> C แบบ sequential
5. Robot 4 ตัวทำงาน concurrent ด้วย asyncio.gather()
6. httpx.AsyncClient ทำให้รอ HTTP แบบไม่ block Event Loop และ reuse connection ได้
7. Success path ส่ง 13 POST requests: reset 1 และ grab 12
8. Timeout หรือ Client error ไม่ได้ยืนยันว่า Server rollback state แล้ว

ประโยคสรุปสำหรับตอบอาจารย์:

โปรแกรมนี้ใช้ httpx.AsyncClient ส่ง HTTP POST ไปยัง Robot Factory API โดย reset
สถานะของรหัสนักศึกษา 6710301033 ก่อน จากนั้นสร้าง coroutine สำหรับ Robot 4 ตัวและรัน
concurrent ด้วย asyncio.gather() ขณะที่แต่ละ Robot ยังใช้ await ใน loop
เพื่อหยิบชิ้นส่วน A, B และ C แบบ sequential ดังนั้น concurrency เกิดข้าม Robot
แต่ไม่ทำลายลำดับงานภายใน Robot แต่ละตัวค่ะ

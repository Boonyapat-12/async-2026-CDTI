บท 6 — Shared State, Race Condition และ asyncio.Lock
========================================================================

[LOCK-01] Race Condition คืออะไร?
ผลลัพธ์ขึ้นกับลำดับหรือจังหวะงานที่เข้าถึง shared state
บน thread เดียวก็เกิดได้ หากหลาย coroutine อ่านค่าเดิมแล้วพัก await ก่อนเขียน
Read–Modify–Write: อ่าน -> คำนวณ -> เขียน ต้องพิจารณาเป็นชุดเดียวกัน
Critical section คือชุดคำสั่งที่ต้องป้องกันการแทรก ไม่ใช่แค่บรรทัดเขียน

ตัวอย่าง interleaving
เริ่ม count=0
A อ่าน 0 -> await; B อ่าน 0 -> await
A เขียน 1; B เขียน 1 -> ได้ 1 แทน 2

[LOCK-02] ป้องกันด้วย Lock
ทุกเส้นทางที่แก้ shared state ต้องใช้ lock ตัวเดียวกัน
async with lock ปลด lock แม้เกิด exception ภายใน
lock.acquire() ต้อง await; lock.release() ไม่ await
อย่าใช้ lock คนละตัวในแต่ละ request เพราะไม่เกิด mutual exclusion
อย่าล็อกกว้างเกินจำเป็น เพราะลด concurrency

[CODE race_vs_lock]
import asyncio  # สร้างงานแข่งกัน
async def trial(use_lock):  # เปรียบเทียบสองวิธี
    state = {"count": 0}  # ข้อมูลร่วมใน trial
    lock = asyncio.Lock()  # lock ร่วมตัวเดียว
    async def update():  # read-modify-write ที่เสี่ยง
        old = state["count"]  # อ่านค่าเดิม
        await asyncio.sleep(0)  # เปิดโอกาสให้งานอื่นอ่านค่าเดียวกัน
        state["count"] = old + 1  # เขียนค่าที่คำนวณ
    async def worker():
        if use_lock:
            async with lock:  # ครอบทั้งชุดอ่านและเขียน
                await update()
        else:
            await update()  # ไม่มีตัวป้องกัน
    await asyncio.gather(worker(), worker())  # เริ่มสองงาน
    return state["count"]  # อ่านผลสุดท้าย
async def main():
    print(await trial(False), await trial(True))  # เปรียบเทียบ
asyncio.run(main())  # รันสคริปต์
[END CODE]

[LOCK-03] ขอบเขตสำคัญ
asyncio.Lock ใช้กับ task ภายใน event loop เดียว ไม่ใช่ thread-safe lock
ไม่ประสานหลาย process / หลาย FastAPI worker / หลายเครื่อง
ระบบเหล่านั้นต้องใช้ transaction, atomic operation หรือกลไกข้าม process
Lock ไม่แก้ deadlock: ถือ lock แล้วรอ coroutine ที่ต้องขอ lock เดิมจะค้าง

server_vulnerable.py ใช้เป็นตัวเปรียบเทียบ; client.py ยิง request ร่วมกัน

1. Asynchronous Programming
===========================

Asynchronous Programming ช่วยให้โปรแกรมสามารถจัดการหลายงานแบบ Concurrent ได้
โดยไม่จำเป็นต้องรอให้งานหนึ่งเสร็จทั้งหมดก่อนจึงเริ่มงานถัดไป

แนวคิดหลัก:

[โค้ด / แผนภาพ : text]
Task A ──► ทำงาน ──► รอ
                    │
                    ▼
                Task B ทำงาน
                    │
                    ▼
                Task A ทำต่อ
[จบโค้ด / แผนภาพ]

จุดสำคัญคือ ไม่ได้หมายความว่า CPU หลาย Core กำลังรันโค้ดพร้อมกันจริง ๆ

2. asyncio และ Event Loop
=========================

Python asyncio ใช้แนวคิด

Single-Threaded Event Loop + Cooperative Multitasking

หมายความว่าในโมเดลนี้ไม่ได้มีการรันโค้ดหลาย CPU Core พร้อมกันในเวลาเดียวกัน

5. Race Condition
=================

Race Condition คืออะไร?
-----------------------

Race Condition เกิดขึ้นเมื่อ ผลลัพธ์สุดท้ายขึ้นอยู่กับจังหวะหรือลำดับการทำงานของ
Concurrent Tasks ที่เข้าถึง Shared Resource โดยไม่มีการประสานงานที่เหมาะสม

พูดง่าย ๆ:

หลาย Task แย่งข้อมูลเดียวกัน แล้วจังหวะการสลับ Task ทำให้ผลลัพธ์ผิด

📌 หน้า 8: Definition of Race Condition

----------------------------------------------------------------

Shared Resource
---------------

คือข้อมูลกลางที่หลาย Task เข้าถึงร่วมกัน เช่น:

- คลังคูปอง
- ยอดเงินในบัญชี
- จำนวนสินค้าใน Stock

6. ทำไม Single-Thread ก็เกิด Race Condition ได้?
================================================

นี่เป็นจุดที่สำคัญมาก

❌ Single-Thread ไม่ได้แปลว่าไม่มี Race Condition

ใน asyncio Race Condition สามารถเกิดขึ้นได้เมื่อ Task ถูกหยุดที่ await ระหว่างกระบวนการ
Read → Modify → Write

ตัวอย่าง:

[โค้ด / แผนภาพ : text]
Task A
อ่านข้อมูล
   ↓
await
   ↓
Task B เข้ามาทำงาน
[จบโค้ด / แผนภาพ]

Task B อาจเข้ามาเปลี่ยนข้อมูลก่อนที่ Task A จะเขียนข้อมูลกลับ

9. Critical Section
===================

Critical Section คือส่วนของ Code ที่เข้าถึงหรือแก้ไข Shared Resource และไม่ควรให้หลาย
Task เข้าไปทำพร้อมกัน

พูดง่าย ๆ:

Critical Section = โซนอันตรายที่ต้องป้องกัน

[โค้ด / แผนภาพ : text]

│       Critical Section       │
│                              │
│  ตรวจสอบคูปอง                │
│  ↓                           │
│  ตัด/นำคูปองออก              │
│                              │
└──────────────────────────────┘
[จบโค้ด / แผนภาพ]

ต้องทำให้ Task เข้าไปทีละตัว

10. asyncio.Lock
================

asyncio.Lock คือ Synchronization Primitive สำหรับ Async Code

หน้าที่หลักคือบังคับให้เกิด

Mutual Exclusion (Mutex)

หมายความว่า:

[โค้ด / แผนภาพ : text]
Lock มีคนถืออยู่
      ↓
Task อื่นเข้าไม่ได้
      ↓
รอ
      ↓
Task เดิมปล่อย Lock
      ↓
Task ถัดไปเข้าได้
[จบโค้ด / แผนภาพ]

เปรียบเทียบง่าย ๆ กับ กุญแจห้องน้ำ

[โค้ด / แผนภาพ : text]
มี 1 กุญแจ
     ↓
คน A ถือกุญแจ → เข้าได้
คน B            → ต้องรอ
     ↓
A คืนกุญแจ
     ↓
B ได้กุญแจ → เข้าได้
[จบโค้ด / แผนภาพ]

13. เปรียบเทียบมี Lock กับไม่มี Lock
====================================

❌ ไม่มี Lock
------------

ตัวอย่าง:

[โค้ด / แผนภาพ : python]
if company_coupons:
    await asyncio.sleep(0.01)
    coupon = company_coupons.pop(0)
[จบโค้ด / แผนภาพ]

ปัญหา:

[โค้ด / แผนภาพ : text]
Task A ตรวจสอบ
    ↓
await
    ↓
Task B ตรวจสอบ
    ↓
Task A/B อาจแย่งข้อมูลเดียวกัน
[จบโค้ด / แผนภาพ]

อาจเกิด:

- Double-pop
- Data corruption
- Crash
- คูปองซ้ำ
- จำนวนคูปองผิด

📌 หน้า 18: Without Lock

----------------------------------------------------------------

✅ มี Lock
------------

[โค้ด / แผนภาพ : python]
async with coupon_lock:
    if company_coupons:
        await asyncio.sleep(0.01)
        coupon = company_coupons.pop(0)
[จบโค้ด / แผนภาพ]

เมื่อ A ถือ Lock:

[โค้ด / แผนภาพ : text]
A → Critical Section
B → รอ
C → รอ
[จบโค้ด / แผนภาพ]

เมื่อ A เสร็จ:

[โค้ด / แผนภาพ : text]
A → Release

[จบโค้ด / แผนภาพ]

14. Key Differences
===================

- หัวข้อ: Data Integrity
  ไม่มี Lock: อาจเกิด Data Corruption
  มี Lock: ข้อมูลสอดคล้องกัน

- หัวข้อ: Critical Section
  ไม่มี Lock: หลาย Task แทรกกันได้
  มี Lock: เข้าทีละ Task

- หัวข้อ: Execution
  ไม่มี Lock: อาจเร็วกว่า
  มี Lock: มีเวลารอ Lock เล็กน้อย

- หัวข้อ: ผลลัพธ์
  ไม่มี Lock: อาจผิด
  มี Lock: ถูกต้องตามการป้องกัน

- หัวข้อ: Race Condition
  ไม่มี Lock: เสี่ยง
  มี Lock: ป้องกันใน Critical Section


เอกสารเน้นว่า ไม่มี Lock อาจเร็วกว่าแต่ผลลัพธ์ผิดได้ ส่วนการใช้ Lock
มีการรอคิวเล็กน้อยเพื่อแลกกับความถูกต้องของข้อมูล

15.2 อย่าเอา Heavy I/O เข้า Lock โดยไม่จำเป็น
---------------------------------------------

เอกสารเตือนว่าไม่ควร Lock งาน I/O ที่ใช้เวลานาน เช่น Network Call ถ้าไม่จำเป็น

เพราะจะทำให้ Async Code กลับมีลักษณะคล้ายการ Block

[โค้ด / แผนภาพ : text]
Lock
 ↓
รอ Network นาน
 ↓
Task อื่นต้องรอ Lock
[จบโค้ด / แผนภาพ]

----------------------------------------------------------------

15.3 กฎจำสำหรับนักศึกษา ⭐
-------------------------

Identify your shared state → locate the await points → protect the read-modify-write
cycle with asyncio.Lock.

แปลให้จำง่าย:

[โค้ด / แผนภาพ : text]
1. หา Shared State
       ↓
2. หา await ที่อยู่ระหว่างการทำงานกับ State
       ↓
3. หา Critical Section
       ↓
4. ครอบด้วย asyncio.Lock
[จบโค้ด / แผนภาพ]

จำนวน Coupon รวมถูกกำหนดตามสูตร:

[โค้ด / แผนภาพ : text]

[จบโค้ด / แผนภาพ]

กลุ่ม 5 คน

[โค้ด / แผนภาพ : text]

[จบโค้ด / แผนภาพ]

[โค้ด / แผนภาพ : text]

1 คน → 1 ใบ
[จบโค้ด / แผนภาพ]

รวม:

[โค้ด / แผนภาพ : text]
8 + 1 = 9 ใบ
[จบโค้ด / แผนภาพ]

กลุ่ม 6 คน
------------

[โค้ด / แผนภาพ : text]

[จบโค้ด / แผนภาพ]

ผลที่ถูกต้อง:

[โค้ด / แผนภาพ : text]
5 คน → คนละ 2 ใบ
1 คน → 1 ใบ
[จบโค้ด / แผนภาพ]

รวม:

23. จำแบบสั้นที่สุดก่อนสอบ ⭐⭐⭐
==============================

Asyncio = หลาย Task ทำงาน Concurrent บน Event Loop

Single Thread ≠ ไม่มี Race Condition

await = จุดที่ Task สามารถคืนการควบคุมให้ Event Loop

Shared State = ข้อมูลที่หลาย Task เข้าถึงร่วมกัน

Race Condition = ผลลัพธ์ขึ้นกับจังหวะการสลับ Task

Read → await → Write = จุดเสี่ยงสำคัญ

Critical Section = ส่วนที่ต้องป้องกัน

asyncio.Lock = Mutex สำหรับ Async Code

Acquire = ขอ/ถือ Lock

Release = คืน Lock

async with lock = วิธีจัดการ Lock ที่แนะนำ

Lock ต้องครอบ Critical Section

อย่า Lock Heavy I/O โดยไม่จำเป็น

เป้าหมายของ Lock = Data Consistency

24. ตารางจำเร็ว
===============

- คำศัพท์: Async Programming
  จำว่า: ทำหลายงานแบบ Concurrent

- คำศัพท์: Event Loop
  จำว่า: ตัวจัดการ Task

- คำศัพท์: await
  จำว่า: คืนการควบคุมให้ Event Loop

- คำศัพท์: Shared State
  จำว่า: ข้อมูลที่หลาย Task ใช้ร่วมกัน

- คำศัพท์: Race Condition
  จำว่า: ผลลัพธ์ขึ้นกับจังหวะ

- คำศัพท์: Read–Modify–Write
  จำว่า: รูปแบบที่เสี่ยง

- คำศัพท์: Critical Section
  จำว่า: โซนที่ต้องป้องกัน

- คำศัพท์: asyncio.Lock
  จำว่า: ตัวป้องกันการเข้าพร้อมกัน

- คำศัพท์: Acquire
  จำว่า: ขอ/รับ Lock

- คำศัพท์: Release
  จำว่า: คืน Lock

- คำศัพท์: async with lock
  จำว่า: ใช้ Lock อย่างปลอดภัย

- คำศัพท์: Mutex
  จำว่า: Mutual Exclusion

- คำศัพท์: server_vulnerable.py
  จำว่า: ไม่มี Lock

- คำศัพท์: server.py
  จำว่า: มี asyncio.Lock

- คำศัพท์: client.py
  จำว่า: ยิง Request Concurrent

25. จุดสำคัญที่สุดที่ควรเข้าใจ
==============================

ถ้าต้องจำเพียงภาพเดียว ให้จำ:

[โค้ด / แผนภาพ : text]
Shared State
     │
     ▼
Task A ──────┐
             │
             ▼
           await
             │
             ▼
Task B ──────┤
             │
             ▼
     แก้ Shared State
             │
             ▼
      Race Condition
[จบโค้ด / แผนภาพ]

วิธีแก้:

[โค้ด / แผนภาพ : text]
             asyncio.Lock
                  │
                  ▼
Task A → [ Critical Section ] → Release
                  │
                  ▼
Task B → [ Critical Section ] → Release
[จบโค้ด / แผนภาพ]

ดังนั้นแก่นของบทนี้คือ:

ปัญหาไม่ได้เกิดเพราะมีหลาย Thread แต่เกิดเพราะหลาย Async Task สามารถสลับกันที่ await
ระหว่างการทำงานกับ Shared State ได้
